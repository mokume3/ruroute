# ruroute の性能改善・軽量化・機能追加の提案

作成日: 2026-11-11

GPT-6 Astra からの提案

優先したいのは、型推論の軽量化、小さなクエリの処理削減、サイズ上限のCI化です。基本的な最適化はすでに進んでいるため、追加機能は実行時コードと型計算の両方への影響を評価します。

## 前提

- 既存APIと、minify後1.5 KB未満という制約を維持する前提です。
- `docs/proposals-for-gemini.md` は参照・変更していません。実装、テスト、既存のベンチマーク資料から独立して検討しました。
- 以下の高速化効果は、比較実装による検証前の仮説です。改善率を保証するものではありません。
- 調査時点の作業ツリーには既存の変更があり、計測値はその状態での結果です。

## 1. 大規模利用向けに返り値の型推論を軽くする

優先度: 高

対象: [src/types.ts](../src/types.ts) の `SortKeys`、`QueryPairs`、`QueryString`、`UrlResult`。

現在はクエリのキーを型レベルでソートし、省略可能なキーの組み合わせも計算しています。組み合わせ数には制限がありますが、その前段のソートは残っています。

入力の型安全性、補完、JSDocを保ちつつ、返り値を `string`、またはパスだけ精密な型にするモードを提案します。既存の精密な返り値型は維持し、大規模プロジェクトで選択できる形が適しています。

呼び出し結果に `: string` を付けるだけでなく、型定義側で重い計算を通らない設計にします。実行時にモード判定を加えず、型側だけで切り替える構成を優先します。

期待する効果:

- エディタの補完・型チェックの負荷削減。
- 実行時コードをほぼ増やさずに、大規模なルート定義へ対応。

検証方法:

- 現在の40ルートに加え、数百ルートで時間・メモリ・instantiation数を比較。
- リテラル引数、`RouteArgs` 型の変数、クエリキー数の多い定義を別々に確認。
- 入力の厳密性とJSDocの引き継ぎが維持されることを確認。

複雑なユニオンの抑制という方向性は、[TypeScript公式の性能指針](https://github.com/microsoft/TypeScript/wiki/Performance)とも整合します。

## 2. 空・少数キーのクエリ処理を削減する

優先度: 高

対象: [src/compile-url.ts](../src/compile-url.ts) の `stringifyQuery`。

現在は `{}` や `{ page: undefined }` でも `URLSearchParams` を生成し、ソートします。

比較する価値があるのは次の2案です。

- 実際に出力する値が見つかるまで、`URLSearchParams` の生成を遅らせる。
- 出力するキーが1種類以下なら、ソートを省略する。

空配列や `undefined` は出力しないため、入力オブジェクトのキー数ではなく、実際に出力するキーを基準にします。配列の値の順序は維持します。

追加した判定が通常のクエリを遅くする可能性があります。空、1キー、複数キー、配列を別々に測り、速度とバンドルサイズの両方で効果がある案だけ採用します。

独自エンコーダへの全面置換は優先しません。[既存の計測資料](./benchmark.md)に遅くなった記録があり、`URLSearchParams` と `encodeURIComponent` には文字の扱いにも差があります。互換性の基準は [WHATWG URL Standard](https://url.spec.whatwg.org/#application-x-www-form-urlencoded-percent-encode-set) を参照します。

## 3. 残っている2段の関数呼び出しを統合できるか試す

優先度: 中

対象: [src/define-routes.ts](../src/define-routes.ts) と [src/compile-url.ts](../src/compile-url.ts)。

現在は、引数の短縮形を解決する関数が `compileUrl` の返す関数を呼んでいます。メソッド間の関数共有は済んでいますが、この2段構造は残っています。

URL生成関数が直接 `params / p`、`query / q`、`hash / h` を受け取る構成にすると、ルートごとのクロージャ数と呼び出し段数を減らせる可能性があります。

評価対象は、大量ルートの初期化時間、保持メモリ、バンドルサイズです。実行エンジンがすでにインライン化している場合、呼び出し速度の改善は小さい可能性があります。

静的・動的パスの分岐で処理の重複が増える可能性もあるため、サイズを確認します。動的パスの遅延分割は維持します。

## 4. サイズ上限と測定ケースをCIで守る

優先度: 高

対象: [scripts/size.ts](../scripts/size.ts)、[bench/url.bench.ts](../bench/url.bench.ts)、[CI](../.github/workflows/ci.yml)。

サイズ計測スクリプトは結果表示のみで、CIにはサイズ上限の判定がありません。全exportは1,500 Bまで約140 Bしか余裕がないため、上限超過を自動で検出します。

1.5 KBを1,500 Bとして扱うかを明文化し、全exportと利用例を別々に監視します。gzip・brotliも併記し、minifiedの削減が転送サイズの削減につながっているか確認します。

ベンチマークには以下を追加します。

- 初回呼び出しと繰り返し呼び出し。
- 空クエリ、キー数の多いクエリ、長い配列。
- 設定オブジェクトの構築時間と、`defineRoutes` 自体の時間の分離。
- 生成結果を利用するケース。
- ルート数を増やしたときの保持メモリ。

現在のルート定義ベンチは設定オブジェクトの生成も含むため、内部最適化の効果が埋もれる可能性があります。前後比較は同じ環境で交互に複数回実施し、数%の差だけでは採用を決めません。

## 追加機能の候補

| 優先度 | 機能                                       | 理由・注意点                                                                                                                                                                            |
| ------ | ------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 高     | `patch` / `head` / `options`               | 現状の `Method` 型は4種類に限定されています。実行時はメソッド名を汎用的に列挙しているため、主に型・テスト・ドキュメントの追加で対応できそうです。                                       |
| 高     | `RouteParams` / `RouteQuery` / `RouteHash` | フォーム、APIラッパー、コンポーネントの引数型に再利用できます。型だけのexportなので実行時JSは増えません。短縮形や省略可能な引数を正しく抽出する設計が必要です。                         |
| 中     | 既存クエリ・ハッシュを持つURLへの対応      | 現状の単純連結では、`/search?lang=ja` にクエリを追加すると `?` が二重になります。外部リンク管理に有用です。上書き・配列・ソート・ハッシュ置換の規則を決め、可能なら定義時に解析します。 |
| 中〜低 | `[...slug]` の配列パラメータ               | ファイルパスや階層ページに便利です。各要素を個別にエンコードして `/` で接続します。型解析と実行時コードの両方が増えるため、サイズを測って判断します。                                   |

可変長パラメータは、現在 `[...slug]` を通常の `...slug` という名前のパラメータとして扱っている点にも注意が必要です。導入時は既存利用との互換性を検討します。

## 優先しない案

- URL生成結果のキャッシュを標準搭載すること。生成処理はすでに軽く、キャッシュキーの生成やメモリ保持のコストが上回る可能性があります。
- `URLSearchParams` を独自エンコーダへ全面置換すること。既存の計測結果とエンコード互換性を踏まえ、再検討には明確な根拠が必要です。
- クエリキーを呼び出しごとに独自ソートすること。既存資料では、事前に挿入ソートしてappendする方式が遅くなっています。
- 動的パスをすべて定義時に分割すること。既存資料で初期化速度の悪化が確認されているため、遅延初期化を維持します。
