## 結論

最初に手を付けるのは次の 6 つ。実行時コードの増加は合計で約 +1 B に収まる。

1. [P1](#p1-サイズの基準を決めて-ci-で上限を判定する) サイズの基準を決めて CI で上限を判定する
2. [P2](#p2-agentsmd-と-packagejson-のコマンド名を揃える) AGENTS.md と `package.json` のコマンド名を揃える
3. [S1](#s1-パスパラメータと-hash-のエンコードを省く-fast-path) + [L2](#l2-get-だけのルートでメソッド用のオブジェクトを作らない) + [L3](#l3-細かいバイト削減) エンコードの fast path と小さなバイト削減
4. [L1](#l1-純粋関数アノテーションで未使用のルート定義を落とす) `@__NO_SIDE_EFFECTS__` の付与
5. [F1](#f1-http-メソッドの追加) `patch` / `head` / `options` の追加
6. [F2](#f2-型ユーティリティの追加) 型ユーティリティの追加

サイズの上限は usage で判定すると決めた(P1)。効果が最も大きい [S2](#s2-クエリを-urlsearchparams-なしで組み立てる)(クエリの自前組み立て)はこの基準なら収まるので、残る判断は壊れた文字列で例外になる挙動の変更を受け入れるかどうか。

## P. 計測と手順

### P1. サイズの基準を決めて CI で上限を判定する

[scripts/size.ts](../../scripts/size.ts) は表を出すだけで、[CI](../../.github/workflows/ci.yml) にサイズの判定がない。今回の 62 B の増加も検知できていなかった。

1. **決定(2026-11-11): 「1.5 KB 未満」は usage で判定し、all exports は記録だけにする。** all exports は名前空間オブジェクトのヘルパ(361 B、F の調査)を含み、バンドラの版で 60 B 単位で動く。このヘルパは `type.number` のように使う利用者のバンドルには入らない。
2. 1.5 KB を 1,500 B と読むことを AGENTS.md に書く。
3. `pnpm size` に上限の判定を足して CI で実行する。gzip と brotli も引き続き出す。
4. [docs/benchmark.md](../benchmark.md) の all exports の値を更新する。

2〜4 は `chore/size-limit-usage` ブランチで実装済み。routopia の行は 1.2.3 での計測値のままで、1.2.4 では再計測していない。

### P2. AGENTS.md と package.json のコマンド名を揃える

AGENTS.md は `pnpm check` / `pnpm coverage` / `pnpm fix` を必須としているが、[package.json](../../package.json) にこの名前のスクリプトはない。実際の名前は `typecheck` + `lint` / `test:coverage` / `lint:fix`。どちらかに揃える。

### P3. ベンチマークのケースを増やす

[bench/url.bench.ts](../../bench/url.bench.ts) の「ルート定義(100 ルート)」は、`Object.fromEntries` と `type.route()` による設定オブジェクトの構築も計測に含んでいる。`defineRoutes` 内部の変更(L2、L4、L5)の効果が埋もれるので分ける。

- 設定オブジェクトの構築と `defineRoutes` を別々に測る
- 空のクエリ、キーの多いクエリ、長い配列、エンコードが要る値と要らない値
- 各ルートの初回呼び出し(遅延分割のコスト)と 2 回目以降
- ルート数を増やしたときの保持メモリ

前後比較は同じ環境で交互に複数回行い、数 % の差だけでは採用を決めない。

## S. 高速化

### S1. パスパラメータと hash のエンコードを省く fast path

`encodeURIComponent` が変換しない文字(英数字と `-_.~!*'()`)だけの値は、そのまま連結する。ID やスラッグはほぼこれに当たる。

```ts
const UNSAFE_COMPONENT = /[^\w.~!*'()-]/

const encodeComponent = (value: ParamValue) => (UNSAFE_COMPONENT.test(value) ? encodeURIComponent(value) : value)
```

`RegExp.prototype.test` は引数を自分で文字列化するので数値も渡せる(TypeScript では引数の型を合わせる必要がある)。出力は現行と同じ(再計測で差 0 件)。

| ケース | 現行 (ops/s) | fast path (ops/s) | 倍率 |
|---|---:|---:|---:|
| パスパラメータ + hash(`{ p: { id: 123 }, h: 'top' }`) | 13,511,142 | 22,183,959 | 1.64x |
| パスパラメータ(`'my-slug_01'`) | 18,604,521 | 28,687,484 | 1.54x |
| パスパラメータ(エンコードが要る `'a b'`) | 16,859,324 | 13,830,857 | 0.82x |
| params + query + hash | 2,614,558 | 2,728,651 | 1.04x |

- サイズ: +21 B(gzip +26 B)。L2 と L3 を合わせるとコアは 851 B → 852 B(F の見積もり)。
- **実装済み**(`perf/encode-fast-path` ブランチ、L2・L3 と同時)。実際の usage は 1,208 B → 1,222 B(+14 B)で、見積もりの +1 B より大きかった。L2 が −7 B ではなく +2 B、hash の判定が −5 B ではなく −3 B だったため。速度は F の実測とほぼ同じ(安全な値で 1.63〜1.72 倍、変換が要る値で 0.83〜0.90 倍)。計測結果は [docs/benchmark.md](../benchmark.md) にある。
- エンコードが要る値では正規表現の検査の分だけ約 2 割遅くなる。パスパラメータに日本語や空白を入れる使い方が中心なら採用しない。
- 数値だけを `typeof` で分ける案は、数値 1.45 倍・文字列 0.96 倍・+29 B で、正規表現の方が速くて小さい。

### S2. クエリを URLSearchParams なしで組み立てる

キーを配列に集めて `sort()` し、文字列連結で組み立てる。`URLSearchParams` が変換しない文字(英数字と `*-._`)だけの値はそのまま使い、それ以外は `encodeURIComponent` の結果に `!'()~` の変換を足して同じ出力にする。

```ts
const UNSAFE_QUERY = /[^\w*.-]/
const FORM_EXTRA = /[!'()~]/g

const escapeFormExtra = (char: string) => `%${char.charCodeAt(0).toString(16).toUpperCase()}`

const encodeQuery = (value: Scalar) =>
  UNSAFE_QUERY.test(value) ? encodeURIComponent(value).replace(FORM_EXTRA, escapeFormExtra) : value

const stringifyQuery = (query: Record<string, QueryValue> | undefined) => {
  if (query == null) return ''
  const keys: string[] = []
  for (const key in query) if (query[key] !== undefined) keys.push(key)
  keys.sort()
  let search = ''
  for (let keyIndex = 0; keyIndex < keys.length; keyIndex++) {
    const value = query[keys[keyIndex]]
    const name = `&${encodeQuery(keys[keyIndex])}=`
    if (Array.isArray(value)) {
      for (let valueIndex = 0; valueIndex < value.length; valueIndex++) search += name + encodeQuery(value[valueIndex])
    } else {
      search += name + encodeQuery(value)
    }
  }
  return search && `?${search.slice(1)}`
}
```

| ケース | Node | Chromium 156 |
|---|---:|---:|
| 数値 1 個(`{ page: 2 }`) | 1.69x | 3.82x |
| 安全な値 3 個 | 1.27x | 1.74x |
| 配列・空白を含む | 0.99x | 1.70x |
| 日本語の値 | 0.85x | 1.51x |

Node は S1 を入れた状態との比較、Chromium はクエリの組み立て関数だけの比較。Safari と Firefox は未計測。

採用の前に決めること:

- **サイズ**: +158 B(gzip +69〜80 B)。S1・L2・L3 を実装した現在の usage 1,222 B に足すと約 1,380 B で、上限まで約 120 B 残る(all exports は約 1,529 B)。usage 基準に決まったので、L4 や L5 を併用しなくても収まる。
- **挙動**: 孤立サロゲート(`'\ud800'` など)を含むキーや値で、現行は U+FFFD に置き換えるが、この案は `URIError` を投げる(再計測で確認)。パスパラメータと hash は現行でも `URIError` を投げるので、そちらに揃う。
- **対象の環境**: エンコードが要る値が中心で Node だけで使うなら遅くなる。

現行と完全に同じ挙動を保つ変種(エンコードが要る値だけ `URLSearchParams` に通す、安全な値だけ自前で組み立てる)は、+124 B / +337 B でどちらも遅く、勧めない。

### S3. 空のクエリで URLSearchParams を作らない

`{}` や `{ page: undefined }` でも `URLSearchParams` を作ってソートしている。出力する値が見つかるまで生成を遅らせ、出力するキーが 1 種類以下ならソートを省く。

- 判定の分だけ通常のクエリが遅くなる可能性がある。空・1 キー・複数キー・配列を別々に測り、速度とサイズの両方で得になる場合だけ採用する。
- S2 を入れる場合は不要(S2 は `URLSearchParams` を使わない)。

### S4. パスパラメータ 1 個の特化

`/users/[id]` のようにパラメータが 1 個のときだけループを通らず直接連結する。分岐の分だけサイズが増え、効果は計測していない。S1 の後に試して、差が出なければ見送る。

### 効果がなかった案(F 実測)

- 引数なしの呼び出しで URL の定数をそのまま返す(G 1-2 と同じ): 1.00〜1.01 倍。
- クエリのキーをソート順に定義して型計算を減らす: instantiation は 241,410 のまま変わらない。

## L. 軽量化

### L1. 純粋関数アノテーションで未使用のルート定義を落とす

`sideEffects: false` が効くのは ruroute のモジュールが丸ごと未使用のときだけ。利用者の `export const routes = defineRoutes({...})` は関数呼び出しなので、`routes` を使っていなくてもバンドラは消せない。

`defineRoutes` と、関数になっている `type.route` / `literal` / `union` / `custom` / `array` / `optional` に `/* @__NO_SIDE_EFFECTS__ */` を付ける。

| 利用者側のバンドル(ルート定義を export するが使わない) | minified |
|---|---:|
| 現行の dist | 1,114 B |
| アノテーションを付けた dist | 33 B |

- F が `dist` を手で書き換えて rolldown 1.3.0 で確認した値。tsdown のビルドでコメントが `dist` に残るかは未確認で、実装時に確かめる。
- [scripts/check-treeshake.ts](../../scripts/check-treeshake.ts) に「使っていないルート定義が消えること」の検証を足す。

**実装済み。** tsdown のビルドでコメントは `dist` に残り、未使用のルート定義は 1,161 B → 38 B になった。`type.route` はオーバーロードの先頭に付けると消えるので、実装のシグネチャの直前に付けている。rolldown は minify しても注釈コメントを残すため、そのまま測ると usage が 1,222 B → 1,383 B(+161 B)に見える。コードは増えていないので、`pnpm size` は注釈を出力せずに測るようにした(決定 2026-11-13)。usage は 1,222 B のまま。

### L2. GET だけのルートでメソッド用のオブジェクトを作らない

```ts
const methods = 'methods' in def ? def.methods : undefined
if (methods) for (const method in methods) fn[method as Method] = fn
else fn.get = fn
```

`type.empty` だけの 100 ルートの定義が 2〜4% 速くなり、−7 B(F 実測)。L5 を採用する場合はそちらに置き換わる。

**実装済み。** `if ('methods' in def) … else fn.get = fn` の形にした。定義は 1.07 倍になったが、サイズは減らず +2 B だった。

### L3. 細かいバイト削減

| 変更 | 増減 | 挙動 |
|---|---:|---|
| `path.startsWith('/')` → `path[0] === '/'` | 約 −8 B | 同じ |
| `hash === undefined \|\| hash === ''` → `(hash ?? '') === ''` | 約 −5 B | `null` を渡すと `#null` ではなく hash なしになる(型では渡せない) |

合わせて −13 B(F の見積もり)。

**実装済み。** hash はキャストを避けるため `hash == null || hash === ''` にした。`path[0] === '/'` で −7 B、hash で −3 B の計 −10 B。

G が挙げた「baseUrl の末尾スラッシュの判定をループの外で 1 回にする」は、判定がパスの先頭の `/` にも依存するので単純には外に出せない。baseUrl を指定したときはキーが `/` で始まることを型で強制しているので実現はできるが、型を通さない入力での挙動が変わり、効果も計測していない。

### L4. ルートごとのクロージャを 1 つにまとめる

`compileUrl` が返す関数と、`params` / `p` などを取り出す関数を 1 つにする。

- サイズ: −36 B
- 速度: 呼び出しは変わらない。100 ルートの定義は 0.91 倍に落ちた(1 ルートあたり約 8 ns、原因は未調査)。保持メモリは未計測。

[docs/benchmark.md](../benchmark.md) でルート定義の速さを示しているので、S2 などでサイズが足りなくなったときの選択肢に留める。

### L5. type.empty / type.route の実行時の形を平らにする

`kind` / `methods` / `'empty'` / `'route'` は minify しても短くならない。実行時は `empty = { get: SCHEMA }`、`route` は受け取ったメソッドの辞書をそのまま返す形にして、`Empty` と `Route` の区別は型だけで行う。`defineRoutes` は常に `for (const method in def)` で回せる。

- 見込み: −40〜80 B(未計測)。`type.route()` がオブジェクトを作らなくなるので、設定オブジェクトの構築も軽くなる。
- **破壊的変更**: `Empty` と `Route` は公開している型で、`kind` と `methods` が見えている。[tests/type.test.ts](../../tests/type.test.ts) も `{ kind: 'empty' }` と `{ kind: 'route', methods }` を検証している。
- メソッドの定義として使う `type.empty`(`delete: type.empty`)と、ルートとして使う `type.empty` が同じ値になる。実行時にメソッドの定義の中身は読まないので動くが、`ValidateMethod` などの `D extends Empty` の判定が型だけの目印で成り立つかを試作で確かめる。

次のメジャー(または 0.x のマイナー)で、L2 の代わりに試作する価値がある。

## T. 型チェックの負荷

### T1. 返り値の型推論を省く軽量モード

返り値の URL 型を推論しなかった頃は、同じ負荷用コードで 84,070 instantiations だった(現状の約 1/3)。入力の型と JSDoc は保ち、返り値を `string`(またはパスだけ精密な型)にする型を選べるようにする。実行時の分岐は足さず、型だけで切り替える。

現状は 40 ルート・クエリキー 10 個でも 0.07 s なので、先に計測だけ行う。[scripts/check-type-perf.ts](../../scripts/check-type-perf.ts) の `ROUTES` を数百に増やし、時間・メモリ・instantiation を確かめる。リテラルの引数、`RouteArgs` 型の変数、キーの多い定義は別々に見る。そこで問題が出たら設計に進む。

### T2. 型計算の細かい削減

- クエリキーが 0〜1 個のときに `SortKeys` と `IsSafeKey` を通さない
- `EncodedParam` の条件型を浅くする

どちらも未計測。キーが 1 個のときの `SortKeys` は 1 回の挿入で終わるので、効果は小さい見込み。`EncodedParam` の分配は `string | number` のユニオンに必要なので、削ると結果が変わるおそれがある。T1 の計測で型の負荷が問題になったときに調べる。

## F. 機能追加

### F1. HTTP メソッドの追加

`Method` 型に `patch` / `head` / `options` を足す。実行時は定義されたキーを `for...in` でそのまま付けているので、実行時コードは変わらない。

- 7 メソッドにすると 241,410 → 248,613 instantiations(+3.0%、F 実測)。
- 3 つの調査すべてが挙げた。G は `patch` だけ、C と F は 3 つ。
- README の Unsupported に「`get` / `post` / `put` / `delete` 以外のメソッド」とある。意図して絞っているなら見送る。追加するなら README も直す。

**実装済み**(決定 2026-11-13: 3 つとも追加)。instantiation は 248,613 で F の実測どおり。usage のサイズは変わらない。README も直した。

### F2. 型ユーティリティの追加

`RouteArgs` と同じ形で公開する。実行時コードは変わらない。

- `RouteParams<T, P, M>` / `RouteQuery<T, P, M>` / `RouteHash<T, P, M>`: 引数の一部だけの型
- `RouteUrl<T, P, M>`: 返り値の URL 型

短縮形(`p` / `q` / `h`)と省略可能な引数から正しく取り出す設計が要る。

### F3. メソッド間で params を共有する

いまはパスパラメータをすべてのメソッドに書く必要がある。ルートの階層で 1 回だけ書けるようにする。

```ts
'/users/[id]': type.route({
  params: { id: type.number },
  get: { query: { tab: type.optional(type.string) } },
  delete: type.empty,
})
```

メソッドを付ける `for...in` が `params` キーも拾うので除外が要る(数 B)。`type.route(params, methods)` のように引数を分ければ実行時コードは変わらない。型への影響は未計測。L5 と同時に行う場合は、定義の形をまとめて設計する。

### F4. params を省略したときの既定の型

`params` を書かなかった `[name]` を `string | number` として扱い、`'/users/[id]': type.empty` を書けるようにする。実行時コードは変わらない。`params` の書き漏れを型エラーで知らせる現在の検証は弱くなる(キーの綴り間違いは引き続きエラーにできる)。

### F5. 可変長パスパラメータ

`[...slug]`(1 個以上)と `[[...slug]]`(0 個以上)。値は `readonly string[]` で、要素ごとにエンコードして `/` でつなぐ。3 つの調査すべてが挙げた。

- 実行時: +80〜120 B(未計測)。S2 と両方入れると usage は約 1,460〜1,500 B で、上限に届く。両方入れるなら L4 か L5 でサイズを空ける。
- 型: `PathParams` と `ReplacePathParams` に分岐が増える(未計測)。
- **破壊的変更**: 現行は `[...slug]` を `...slug` という名前の通常のパラメータとして扱い、README にもそう書いてある。
- スキーマの書き方は 2 案ある。`type.array(type.string)` を `params` でも許す(G)か、パスの書き方から自動で配列にする(F4 と組み合わせる)か。

### F6. ルート単位でツリーシェイクできる定義

`defineRoutes` は 1 つのオブジェクトを返すので、使っていないルートを個別には消せない。1 ルートを 1 つの関数として返す export を足す。

```ts
export const userRoute = defineRoute('/users/[id]', { get: { params: { id: type.number } } })
```

L1 のアノテーションと組み合わせると、import されなかったルートは定義ごと消える。`compileUrl` をそのまま使えるので追加のコードは小さい見込み(未計測)。

### F7. クエリやハッシュを含むキーへの対応

現行はキーの文字列にそのまま連結するので、`'/search?lang=ja'` というキーにクエリを渡すと `?` が 2 つになる。外部リンクの管理で起こりうる。

対応するなら、定義時にキーを解析し、上書き・配列・ソート・ハッシュの置き換えの規則を決める必要がある。実行時コードと型の両方が増えるので、まずは「キーに `?` と `#` を書かない」ことを README に書くか型でエラーにする方が小さく済む。

### F8. ルートのパターン文字列を参照できるプロパティ

ルートの関数に、置換前の文字列(`'/users/[id]'`)を持たせる。関数を別の場所へ渡した後でも、ログやキャッシュキーで「どのルートか」を参照できる。

- 実行時は代入 1 つで数 B(未計測)。`Routes` の型にも足す。
- baseUrl を含めるかどうかと、プロパティ名を決める必要がある。ルートのオブジェクトから取り出す時点ではキーがそのままパターンなので、必要になる場面は限られる。

### F9. パスパラメータのリテラル型を返り値に反映する

`type.literal(['v1', 'v2'])` のパラメータを、返り値で `` `/${'v1' | 'v2'}/users` `` にする。`encodeURIComponent` で変わらない文字だけのリテラルに限れば型と実際の URL は一致する(`IsSafeKey` と同じ検査が使える)。呼び出しの引数から `/users/123` まで絞るには `params` にも `const` の型引数が要り、instantiation が増える。T1 と逆向きなので、型の負荷を測ってから判断する。

### F10. パターン変換と URL のマッチを別エントリで提供する

- `'/users/[id]'` → `'/users/:id'` の変換(Hono / Express などへの登録用)
- URL からルートと `params` を逆引きするマッチ

`ruroute/pattern` のような別エントリにすればコアのサイズは変わらない。README の Unsupported に「URL のパース」とあるので、方針として入れないなら見送る。

### F11. ルート定義の分割とプレフィックス

機能ごとに定義を分け、`/api/v1` のような共通のプレフィックスを付ける。分割だけなら、いまでも `routes: { ...userRoutes, ...postRoutes }` と書ける(公開している `ValidRoutes` でラッパー関数の引数も検証できる)。プレフィックスはキーの型を書き換える必要があり、具体的な設計はまだない。要望が出てから検討する。

## 見送り

| 案 | 出典 | 理由 |
|---|---|---|
| 定義時にクエリキーをソートしておく | G 1-1 | メソッド間の関数の共有と両立しない([統合時に直した点](#統合時に直した点)) |
| `type.empty` のルートを定数を返す関数にする | G 1-2 | 効果なし(F 実測) |
| URL 生成結果のキャッシュ | C | 生成はすでに軽く、キーの生成とメモリのコストが上回る |
| クエリキーを呼び出しごとに挿入ソートして `URLSearchParams.sort()` を省く | C | 過去の計測で約 2% 遅くなった |
| 動的パスをすべて定義時に分割する | C | 過去の計測で定義が約 88% に落ちた |
| 実行時の値の検証(zod などとの連携) | F | 「型だけで実行時は何もしない」という設計と逆向きで、サイズも大きく増える |
| クエリ配列の書式の切り替え(`tags[]=a` など) | F | 呼び出しごとの分岐が増える。要望が出てからでよい |
| Proxy でルートを遅延生成する | F | 呼び出しのたびにトラップを通る(未計測) |

## 決めること

決定済み:

- サイズの上限は usage で判定する(P1、2026-11-11)。
- `patch` / `head` / `options` を追加する(F1、2026-11-13)。
- サイズは注釈コメントを出力せずに測る(L1、2026-11-13)。

## 進め方

1. P1・P2・P3。以降の変更の効果と退行を測れるようにする。
2. L2 + L3 + S1。合わせて +1 B で、パスパラメータの呼び出しが約 1.5 倍になる。

4. F1 と F2。実行時コードに触れない。

7. L5 の試作。採用するなら F3 と合わせて定義の形を決める。
8. F4〜F11 は要望と残りのサイズを見て個別に判断する。
